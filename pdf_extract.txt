1.1 What this document covers
How the exercise and meal databases built by build_catalog_db.py  are consumed by a language model
hosted on Ollama Cloud, and how the Flutter app, a gateway service and the Ollama Cloud API fit together
to produce a chatbot that recommends real catalog items  and deep-links to the screens that already exist
in the app.

The single most important design rule in this document:
The model never sees the database and never invents an identifier.  It emits tool calls  describing what
it wants; the gateway compiles those into parameterised SQL; the rows that come back are the only
exercises and meals the model is permitted to cite.
Everything else — streaming, deep links, offline behaviour, error handling — follows from that rule. None
of it depends on where the model runs, because retrieval was never the model's job.
1.2 Why a gateway exists at all
It is tempting to have the Flutter app call Ollama Cloud directly. Don't. The thing you would be shipping
into the app is a credential attached to your account and your bill .
The API key cannot live in the app.  A key shipped in a binary is a key in the hands of anyone who
unzips the binary. It is not obfuscatable and not revocable per user — you would be rotating a single
key against the entire installed base. The key belongs in the gateway's secret store and nowhere else.
Ollama Cloud has no concept of your users.  It authenticates your account, not your customers. Per-
user rate limits, quotas and bans can only exist on a server you control.
Quota is a shared, exhaustible resource.  One abusive client can spend the allowance that every other
user depends on. Only the gateway can meter that.
Prompts change constantly.  The system prompt is the thing you will iterate on most. On the server it
is a config file; in the app it is an App Store review.•

horizontally.

2.2 Design decisions that matter downstream
Exercise ids are slugs derived from the name.  The source data has no id field at all. 
slugify("Bodyweight Glute Bridge")  → bodyweight-glute-bridge . This is the only identifier that ever
leaves the system: the model emits it, go_router  routes on it, analytics key on it. Renaming an exercise
changes its id, so treat renames as a migration.
Muscles are keyed by name, never by the source id.  In prime_mover_muscles.json , 26 rows share only

Difficulty has a canonical rank.  The source file's array order is not the progression — it lists Intermediate

Every "no value" spelling becomes SQL NULL. The source uses "", "-", "N/A", "Unsorted*"  and

3.1 The principle
The model has no database driver, no network access and no knowledge of your catalog. What it has is:
A vocabulary  — the legal values for every filter, ~500 tokens in the system prompt, generated from
the database at boot.
Three tools  — search_exercises , search_meals , search_by_text , whose arguments are exactly
those vocabulary values.
A candidate set  — the ≤8 rows the gateway retrieved for this turn , injected as a tool result.
It may only cite ids from (3). Everything else is enforced by the gateway.
Why not put the catalog in the prompt?
At roughly 120 tokens per exercise, 3,000 exercises is ~360,000 tokens . That exceeds even 
gemma4:31b 's 256K window, and the quality would collapse long before the limit. Capacity is only the first
objection. The harder one is cost: you would be paying GPU-time to re-read the entire catalog on every
turn, forever, to answer a question that a 4 ms indexed SQL query answers exactly. The vocabulary is 500
tokens and the candidates are 700 — a 300× reduction that also makes the model's output verifiable.
Why not embeddings?
Structured facets (muscle group, equipment, difficulty, movement pattern) are exactly what fitness
questions filter on, and SQL answers them exactly, instantly and explainably. Embeddings would add an
on-device model, ~10 MB of vectors and fuzzy results for a problem that has a precise answer. The one
thing they'd add — matching phrasings the vocabulary doesn't cover — is handled by search_by_text
over FTS5.

Six details in that loop are load-bearing:
Every call carries HEADERS . There is no unauthenticated path to ollama.com , and no default that will
save you if you forget.
"think": False  is explicit on both calls rather than left to the default (§3.12).
Both calls pass through the concurrency gate from §4.6, but at different levels. Turn A goes through 
post_json , which takes and releases the slot itself on each attempt — so a backoff never idles the
account's only slot, and the SQL retrieval that follows never holds one open. Turn B streams, so it
holds the slot explicitly for the duration of the generation. Do not wrap a post_json  call in 
upstream_slot()  as well — with MAX_INFLIGHT=1  that is a self-deadlock, and it is the easiest mistake
to make in this file.
post_json  replaces the bare client.post  so retries and error mapping (§4.6) live in one place.
raise_for_upstream(resp)  on the streaming call rather than a bare raise_for_status() . A 429
arrives as an HTTP status before any body; mapping it to the same typed exceptions post_json  raises
is what makes the quota path in §4.10 reachable from turn B — which is the longer and more likely-
throttled of the two turns. Silently iterating an error response produces an empty reply instead of a
handled failure.
handle_chat  wraps the whole thing. Nothing calls chat directly.  Every typed upstream failure lands
in chat_degraded  (§4.11) rather than in a stack trace.
chars counts characters, not tokens. Name it that way in the log and in the SSE payload, or somebody
will eventually cost the feature with it.
sanitize(args)  drops keys the tool schema doesn't define and coerces types — a model will
occasionally return "max_difficulty": "2"  as a string.

Sizing MAX_INFLIGHT . Set it to your plan's concurrent-model allowance — 1 on the Free plan. Making it an
environment variable is the whole point: upgrading the plan should be a deploy, not a patch. Setting it
higher than your plan allows does not buy throughput; it converts your own orderly queue into upstream
429s.
This semaphore is per process, and your plan's allowance is per account.  Two workers, or two
replicas behind a load balancer, give you 2× MAX_INFLIGHT  in flight upstream — exactly the situation the
gate exists to prevent. Until you are on a plan whose allowance comfortably exceeds your replica count,
either run a single process, or set MAX_INFLIGHT = plan_allowance / replica_count  and accept the
rounding, or move the gate into Redis. Whichever you pick, write it down next to the deployment
config, because the day someone scales the gateway to two pods is the day the 429 rate goes up for
no visible reason.

Retries, carefully.  Retry connection errors and 5xx; never retry 401/403 (the key is wrong and will still be

failures). Never retry a 4xx you caused — UpstreamRejected  means your tools or format payload is
malformed, and it should page you, not loop.

bubble, and replaying them would duplicate text. Retry turn B only when chars == 0  — that single
condition is what makes the "retry once at temperature 0.3 " row in §4.10 safe, and it is the rule to state in
the code review.

4.8 Auth, rate limiting and quota
There are now two distinct budgets to protect: your users' fair access to the service, and your account's
finite allowance upstream. They need separate mechanisms.
Protecting the key
The key lives in a secret manager and reaches the process as an environment variable. Never in the
repo, never in an image layer, never in a log line, never in an error message returned to the app.
Keys do not expire on their own. Rotation is manual: create the new key, deploy it, then revoke the old
one at ollama.com/settings/keys . Do it on a schedule and on every person-leaves-the-team event.
Assert at boot that OLLAMA_API_KEY  is present and non-empty. A gateway that starts without a key and
fails on the first user message is worse than one that refuses to start.
Protecting your users from each other
Verify the app's JWT (Firebase, Supabase, whatever you already use) on every request. Reject
anonymous traffic — an open proxy to a paid inference account is a very expensive thing to leave
running.
Two limits: a short-window rate limit and a rolling monthly quota per user. Size the short window
against your account  throughput, not against what feels generous — §3.14 puts a single free
concurrency slot at roughly 15–30 messages/minute for everyone combined , so a 20/minute per-user
limit lets one person consume the entire service. Something around 6/minute is defensible while 
MAX_INFLIGHT  is 1; raise it with the plan. Return 429 with a Retry-After ; the app shows a friendly
chip.
Cap message  length (~2,000 chars) and history length server-side. Both are prefill you pay for.•

7.7 Risks
Data quality is the top risk, not the model.  Every unresolved muscle name and duplicate slug in 
validation_report.json  becomes an unexplainable chatbot bug three layers away. Gate the build on it.
This outranks everything below.
There is a third-party dependency in the critical path.  No SLA to point at, no support contract, and no
way to make an incident on someone else's infrastructure resolve faster. The mitigation is not to avoid the
dependency — it is to make the failure boring. §4.11 is that mitigation, and it belongs in phase 4, not in a
backlog. Treat "the model is unavailable" as a normal operating state that happens a few times a year, not
as an emergency.
The model can change underneath you.  A hosted tag is not a checksum. The weights behind 
gemma4:31b  can be updated without your involvement, and the failure mode is subtle: not an error, but a
slow drift in tool-argument choices or output style that shows up as a rising refs_dropped  rate weeks
later. Mitigations: the deploy-time assertion in §7.3, the scheduled eval run in §7.5, and alerting on 
refs_dropped . Do not assume you would notice by reading replies.
User text leaves your infrastructure.  This deserves an explicit decision, not an assumption. Fitness chat
contains health information — injuries, weight, medication, pregnancy, eating patterns. Every message is
transmitted to a third party and processed primarily in the United States, with possible routing to Europe
and Singapore. Ollama states that prompt and response data is never logged or trained on. Three things
follow:
Your privacy policy must say this. "We process your messages using a third-party AI provider" is the
minimum; naming the provider and the regions is better.
Minimise what you send. The profile block in §3.3 carries limits — free text where users write real
medical detail. Consider constraining it to a controlled vocabulary, or omitting it from the prompt and
applying it as a retrieval filter instead. The gateway is the right place to strip anything the model
doesn't need.
If you have users in jurisdictions with data-localisation requirements, or if you ever pursue a health-
data compliance regime, revisit this before it becomes expensive to reverse. The architecture makes
reversal cheap — one URL and one auth header, and §4.6 is the only module that would change —
which is a reason to keep it that way.
Quota economics.  The question to answer before launch is "what does one message cost, and what
does that multiply to". You cannot read your quota from the API (§3.14), so you must instrument for it. Do•

Arabic quality.  A 31B model should handle Arabic noticeably better than the small models that fit on a
single GPU — but that is an expectation, not a result, and Arabic is consistently the weaker side of
bilingual open models. Test early with real Arabic questions, not translations of your English ones. If it falls
short, the fix is cheap: route by detected locale to a different model for Arabic only. That is a string in a
config file here, where on your own hardware it would be a second GPU.
Safety scope.  Fitness chat drifts into medical, injury and disordered-eating territory quickly. Rule 6 in the
system prompt plus safety_flag  is necessary but not sufficient; add an output-side classifier for those
topics and a canned, humane response. Run that classifier on your gateway, not as a second model call —
it must still work in degraded mode, when there is no model to ask.
Nutrition estimates. nutrition_is_estimate  defaults to 1 for every meal. If the UI or the model ever
presents those numbers as exact, users will make real decisions on fabricated data. Keep the "estimated"
badge, and fill ingredient.*_100g  from USDA FoodData Central to make the numbers real.

Candidate set  — the ids retrieval returned for one turn. The model may cite nothing else.
Card — a row of exercise_card  / meal_card . The unit of exchange between retrieval, the model, the
gateway and the UI.
Degraded mode  — serving retrieval results with a canned line when the model is unreachable, out of
quota, or erroring. See §4.11.Appendix C — Reference Fitness Chatbot — Ollama Cloud Integration
v1.1 · 2026-07-25 61Facet — a structured filter (muscle group, equipment, difficulty rank, movement pattern). What tool
arguments compile into.
Fast path  — skipping turn A when a regex classifier extracts facets confidently. On cloud, the primary
cost lever. See §4.7.
Gateway  — your server between the app and Ollama Cloud. Owns the prompt, retrieval, validation, the
API key and the upstream concurrency budget.
GPU-time  — Ollama Cloud's unit of metering. Not tokens, not requests. Driven by model weight class,
generation length and prompt length.
Ollama Cloud  — Ollama's hosted inference service, reached at https://ollama.com/api/*  with a bearer
API key. Same API as the local daemon, minus num_ctx  and keep_alive .
Prime mover  — the muscle primarily responsible for a movement. role='prime'  in exercise_muscle .
Ref — an id the model returned in exercise_refs  / meal_refs , before validation.
Relaxation ladder  — the fixed order in which filters are dropped when a query returns nothing.
Slug — a URL-safe id derived from a name ( Bodyweight Glute Bridge  → bodyweight-glute-bridge ).
Snapshot  — denormalized card data the gateway attaches to each ref so an app with an older database
can still render it.
Structured output  — Ollama's format parameter constraining generation to a JSON Schema. Works
identically on cloud models.
Thinking  — gemma4's optional reasoning pass, returned in message.thinking . Disabled via 
"think": false . See §3.12.
Turn A / Turn B  — the tool-calling round trip and the answer-writing round trip. Two upstream requests,
two occupancies of your concurrency slot.
Vocabulary block  — the ~500-token list of legal filter values embedded in the system prompt, generated
from the database.
